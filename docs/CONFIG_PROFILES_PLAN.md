# План перехода Citadex на конфигурационные профили

## Цель

Упростить запуск Citadex до двух сценариев:

1. Первый запуск `Citadex.exe` открывает мастер создания конфигурации.
2. Последующие запуски сразу используют активный профиль.

API-ключи и пользовательские настройки не должны храниться в `.venv`, каталоге проекта или внутри `.exe`. `.venv` остаётся только средой разработки. Пользовательские данные хранятся в `%APPDATA%\Citadex`.

## Итоговый пользовательский сценарий

### Первый запуск

Мастер последовательно запрашивает:

1. Название профиля, например `NVIDIA Fast`.
2. Провайдера: `nvidia`, `openai`, `ollama` или `local`.
3. API-ключ для облачного провайдера.
4. Точное имя модели.
5. Режим: `chat` или `agent`.
6. Политику разрешений для agent-режима: `ask` или `auto`.
7. Рабочую папку.

Перед сохранением облачного профиля Citadex должен проверить ключ и наличие модели у выбранного провайдера. После успешной проверки профиль становится активным и запускается основное приложение.

### Последующие запуски

Если активный профиль корректен, Citadex показывает короткий экран:

```text
PROFILE     NVIDIA Fast
PROVIDER    NVIDIA
MODEL       z-ai/glm-5.2
MODE        CHAT

ENTER       продолжить
C           открыть настройки
```

Никакие каталоги моделей не загружаются при обычном запуске. Проверка выполняется только при создании или изменении профиля и по явной команде пользователя.

### Изменение настроек

Вместо `/keys`, `/provider` и автоматического определения провайдера используется одна команда:

```text
/config
```

Меню `/config`:

1. Выбрать профиль.
2. Создать профиль.
3. Изменить профиль.
4. Проверить профиль.
5. Удалить профиль.
6. Отмена.

Удаление активного профиля должно потребовать подтверждения. После удаления выбирается другой профиль либо запускается мастер создания.

## Формат хранения

### Несекретные настройки

Файл `%APPDATA%\Citadex\config.json`:

```json
{
  "version": 2,
  "active_profile": "nvidia-fast",
  "profiles": {
    "nvidia-fast": {
      "name": "NVIDIA Fast",
      "provider": "nvidia",
      "model": "z-ai/glm-5.2",
      "mode": "chat",
      "permissions": "ask",
      "project_root": "C:\\Users\\user\\Projects\\demo"
    },
    "openai-agent": {
      "name": "OpenAI Agent",
      "provider": "openai",
      "model": "gpt-5-nano",
      "mode": "agent",
      "permissions": "ask",
      "project_root": "C:\\Users\\user\\Projects\\demo"
    }
  },
  "recent_projects": []
}
```

Идентификатор профиля должен быть стабильным, уникальным и не зависеть от отображаемого имени после создания.

### API-ключи

Первый вариант реализации использует `%APPDATA%\Citadex\.env`:

```dotenv
CITADEX_PROFILE_NVIDIA_FAST_API_KEY="nvapi-..."
CITADEX_PROFILE_OPENAI_AGENT_API_KEY="sk-..."
```

Требования:

- никогда не выводить значение ключа;
- не сохранять ключ в `config.json`, логах или истории сессии;
- ограничивать права файла текущим пользователем, где это поддерживается;
- обновлять и удалять ключ только через слой `core.credentials`;
- в будущем предусмотреть замену `.env` на Windows Credential Manager без изменения формата профилей.

## Изменения архитектуры

### 1. Модель данных профиля

Добавить `core/config_profiles.py`:

- `ConfigProfile` — dataclass одного профиля;
- `ProfileStore` — версия, активный профиль и словарь профилей;
- `load_profile_store()`;
- `save_profile_store()` с атомарной записью через временный файл;
- `create_profile_id()`;
- `validate_profile()`;
- `get_active_profile()`;
- `set_active_profile()`;
- `delete_profile()`.

Валидация должна отклонять неизвестного провайдера, пустое имя модели, неверный режим, неверные разрешения и отсутствующую рабочую папку.

### 2. Хранение ключей по профилям

Переработать `core/credentials.py`:

- заменить ключи, привязанные только к провайдеру, ключами профиля;
- добавить `profile_key_name(profile_id)`;
- добавить `save_profile_api_key(profile_id, provider, key)`;
- добавить `load_profile_api_key(profile_id)`;
- добавить `delete_profile_api_key(profile_id)`;
- сохранить проверку формата NVIDIA-ключа;
- для `ollama` и `local` не создавать запись ключа.

Нельзя использовать имя профиля напрямую как имя переменной без нормализации.

### 3. Мастер конфигурации

Добавить `core/config_wizard.py`:

- `create_profile_interactively(console, existing=None)`;
- последовательный ввод полей;
- повторный запрос при ошибке;
- проверка API-ключа;
- проверка указанной модели только у явно выбранного провайдера;
- сохранение только после успешной проверки;
- возврат готового `ConfigProfile`.

Мастер не должен автоматически угадывать провайдера по модели.

### 4. Запуск приложения

Изменить `main.py`:

- загрузить `ProfileStore` до создания `SessionSettings`;
- при отсутствии профилей запустить мастер;
- получить ключ активного профиля;
- создать `SessionSettings` из профиля;
- убрать раздельные ветви настройки ключа, провайдера и модели;
- сохранить CLI-флаги `--provider` и `--model` только при необходимости для автоматизации либо удалить их как отдельное согласованное изменение;
- при смене режима через `/mode` менять только текущую сессию, если пользователь явно не сохраняет профиль.

### 5. Команда `/config`

Добавить обработчик конфигураций отдельно от основного `handle_slash`, например в `core/config_commands.py`.

После выбора или изменения профиля обработчик должен:

- обновить активный профиль;
- сбросить текущий LLM-клиент;
- обновить `SessionSettings`;
- показать провайдера, модель и режим;
- не требовать перезапуска приложения.

После появления `/config` удалить:

- `/keys`;
- `/provider`;
- отдельный интерактивный `/model` для облачных профилей;
- `resolve_cloud_model_provider()`;
- связанные меню и тесты автоматического определения;
- неиспользуемые функции управления ключами по провайдерам.

Решение о сохранении `/model` для временной смены модели внутри текущего профиля нужно принять до удаления. Рекомендуемый вариант: изменение модели выполняется через `/config`, чтобы состояние не расходилось с сохранённым профилем.

### 6. Клиенты провайдеров

Оставить общий `CloudClient`, `NVIDIAClient` и `OpenAIClient`.

Создание клиента должно принимать уже полностью проверенный профиль и ключ. Клиент не должен читать глобальные переменные окружения самостоятельно. Рекомендуемая сигнатура:

```python
create_client(profile: ConfigProfile, api_key: str, system_prompt: str)
```

Это устранит скрытую зависимость от активного окружения и исключит смешивание модели одного провайдера с ключом другого.

### 7. Сборка EXE

Использовать существующий PyInstaller-процесс и обновить `.spec` при добавлении новых модулей.

Проверить два варианта:

- `Citadex.exe` — облачные провайдеры и Ollama;
- `Citadex-Local.exe` — встроенная локальная модель.

`Citadex.exe` не должен содержать пользовательские ключи или готовый `config.json`. При первом запуске он создаёт файлы в `%APPDATA%\Citadex`.

## Миграция существующих пользователей

При первом чтении конфигурации версии 1:

1. Прочитать старые `provider`, `models`, `mode`, `permissions` и `project_root`.
2. Создать один профиль `Migrated profile`.
3. Перенести соответствующий ключ из `NVIDIA_API_KEY` или `OPENAI_API_KEY` в ключ профиля.
4. Не переносить ключ другого неактивного провайдера автоматически.
5. Сохранить резервную копию старого `config.json` как `config.v1.backup.json`.
6. Записать конфигурацию версии 2 атомарно.
7. Повторный запуск миграции не должен создавать дубликаты.

После стабильного релиза можно добавить отдельный импорт второго старого ключа через `/config`.

## Тесты

### Unit-тесты

- создание и нормализация ID профиля;
- сериализация и загрузка `ProfileStore`;
- повреждённый или неизвестный формат конфигурации;
- атомарное сохранение;
- создание, замена и удаление ключа профиля;
- отсутствие ключей в `repr`, сообщениях и `config.json`;
- мастер для NVIDIA, OpenAI, Ollama и local;
- повторный ввод после неверного ключа или модели;
- выбор, изменение и удаление профиля;
- сброс клиента после смены активного профиля;
- невозможность смешать NVIDIA-модель с OpenAI-ключом;
- миграция версии 1 в версию 2;
- идемпотентность миграции.

### Интеграционные тесты

- первый запуск без конфигурации;
- повторный запуск с активным профилем;
- переключение профиля без перезапуска;
- запуск собранного `.exe` в чистой тестовой папке пользователя;
- отсутствие `.venv` рядом с `.exe`;
- отсутствие секретов в собранных файлах и логах.

### Проверки перед выпуском

```powershell
python -m pytest
ruff check main.py citadex_api.py citadex_local.py citadex_smoke.py citadex_windows.py core tests
python -m mypy main.py citadex_api.py citadex_local.py citadex_smoke.py citadex_windows.py core
python -m build
```

После этого выполнить smoke-тест обоих `.exe` на машине или в профиле Windows без установленного Python.

## Рекомендуемые коммиты

1. `test: define configuration profile behavior`
2. `feat: add versioned profile storage`
3. `feat: store API credentials per profile`
4. `feat: add first-run configuration wizard`
5. `refactor: create clients from active profiles`
6. `feat: replace provider commands with config command`
7. `feat: migrate legacy user configuration`
8. `build: package profile workflow in Windows executables`
9. `docs: document profile setup and migration`

Каждый коммит должен проходить относящиеся к нему тесты. Полный набор проверок обязателен перед последним коммитом.

## Критерии готовности

- новый пользователь запускает `Citadex.exe` без Python и `.venv`;
- мастер создаёт рабочий профиль за один проход;
- повторный запуск не спрашивает ключ, провайдера или модель;
- пользователь может переключить профиль одной командой `/config`;
- модель никогда не отправляется другому провайдеру;
- ключи отсутствуют в репозитории, JSON, логах и выводе;
- обычный запуск не делает запрос к каталогу моделей;
- смена профиля применяется без перезапуска;
- старые настройки безопасно мигрируются один раз;
- тесты, Ruff, mypy, сборка и smoke-тест `.exe` проходят.

## Что не входит в первый этап

- синхронизация профилей между компьютерами;
- облачное хранение ключей;
- графический интерфейс;
- автоматический выбор «лучшей» модели;
- измерение стоимости запросов;
- Windows Credential Manager, если это требует новой зависимости или отдельного системного интеграционного слоя.
